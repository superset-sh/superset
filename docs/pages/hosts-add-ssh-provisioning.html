Superset · CLI review

One command turns a bare box into a host

superset hosts add user@host probes a machine over SSH, installs the CLI only if it is missing, mints a device-scoped API key, starts the host service, and waits for the cloud to confirm the host is online. Nobody has to sit at the far end.

01

What it does

Nothing in the repo took an SSH target before this. Hosts were onboarded either by someone sitting at the machine with the desktop app, or by hand over SSH — apps/review-host/ is that second path written out longhand for exactly one VM. This generalises it into the CLI, next to the hosts list · wake · set-wake that already existed. 

# the whole flow, unattended
superset hosts add ubuntu@devbox --org acme --yes

# a box behind a non-standard port, with a specific key and a pinned version
superset hosts add ubuntu@devbox:2222 --identity ~/.ssh/id_devbox --version 1.30.2

Registration needs no second step: host.ensure inserts the owner row itself on first connect, so a box that reaches the relay is already claimed by the key's user. That was established end-to-end in plans/20260710-headless-host-registration-fixes.md; this command relies on it rather than re-implementing a pairing handshake.

03

Five traps, each handled in code

These are not hypotheticals. Each one is either documented in this repo as something that already went wrong, or verifiable on a shell in thirty seconds — and each would have made "connects automatically" false in a different way.

01PATH is a lie right after installing

The installer appends its export PATH to .zshrc or .bashrc, but ssh host 'cmd' runs a non-interactive shell that never reads them — zsh sources only .zshenv, and Ubuntu's stock .bashrc returns early when non-interactive. I confirmed both on a shell. So a CLI installed one line earlier is invisible to command -v on the next.

The probe checks $SUPERSET_HOME/bin, ~/superset/bin, ~/.local/bin and /usr/local/bin before PATH, and the setup script always invokes "$BIN" by absolute path. A test asserts the script never calls superset by bare name.

02The wrong org is silently unreachable

Registering a host under the wrong organization gets it rejected by the relay with an opaque 1008 Forbidden — hours of debugging, per the headless-registration plan. start already refuses to guess between multiple memberships.

Org is resolved explicitly through resolveOrganization with no active-org fallback, matching start. Non-interactive with several memberships and no --org is an error listing them, never a guess.

03Cloned machines collide on host id

getHostId() is an HMAC of /etc/machine-id. Containers without systemd have an empty one, so every such box derives the same id (a5b47ded…) and they evict each other's relay tunnel in a loop. The review-host README documents this the hard way; VM images cloned from a template have it too.

An empty machine-id is a hard error naming the collision and pointing at systemd-machine-id-setup, with --allow-shared-machine-id as the deliberate override.

04Progress output would corrupt --json

--json is auto-on under CI and agent environments, and clack draws spinners on stdout — so the pretty progress would wrap the JSON result in chatter and break every caller that parses it.

A small Progress seam: the real clack implementation on a TTY, a silent no-op otherwise. Interactivity also decides BatchMode=yes, so ssh fails fast instead of hanging on a password prompt no one can answer.

05Shell injection through ordinary values

The API key, org id and binary path are all interpolated into a script another machine executes. An unlucky or hostile value is arbitrary code on someone else's box.

Everything interpolated goes through POSIX shellQuote, asserted by round-tripping command substitution, backticks, embedded quotes and newlines through a real sh rather than against an expected spelling.

06

Two calls worth your eyes

Both are deliberate trade-offs rather than oversights, and both are cheap to change if you read them differently.

The key is in argv for one call

It travels to the box on stdin everywhere except auth login --api-key, which accepts a key only as a flag because it inspects process.argv directly. For that one call the key is visible to ps on that machine.

Buying: a device that stays logged in across reboots. The alternative is the daemon holding the key only in its environment, gone on restart. Worth teaching auth login to read the key from stdin instead?

No service unit, per your call

start --daemon detaches and unrefs, so the host survives the SSH session closing but not a reboot. Nothing in the CLI writes a systemd unit or launchd plist — start only prints a hint suggesting one, and apps/review-host hand-rolls its own.

A --persist flag that installs the unit is the obvious follow-up, and the review-host scripts are a working template for it. Ticket, or leave it?
