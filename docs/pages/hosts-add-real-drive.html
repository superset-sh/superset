Three things I could not do, said plainly

The ask was a CDP-driven, filmed, end-to-end success run. Each of those three hit a wall that is real rather than incidental, so here is what I did instead of quietly substituting something weaker.

CDP does not apply to this change

The Chrome DevTools Protocol drives the desktop app's renderer. hosts add is a CLI command with no UI — there is no element to click and no DOM to assert on. CDP could only have shown the host appearing in the app afterwards, which needs the step below that cannot run here anyway.

The full flow cannot complete from a cloud workspace

Not a limitation to engineer around — a deliberate security boundary. SANDBOX_ALLOWED_PROCEDURES is an allowlist of 18 procedures, and two of the three API calls this command makes are outside it.

There is no film

No screen recorder and nothing visual to record. What follows is the real terminal output, captured verbatim as it ran — the honest equivalent for a command-line flow. Nothing below is typed by hand or reconstructed.

The drive found a bug

This is the part a staged demo would never have produced. I built a second container with an emptied /etc/machine-id to watch the collision guard refuse it. It did not refuse it.

Why it was wrong

getHostId() reads /etc/machine-id and falls back to the dbus file only when that read throws. A file that exists but is empty returns "" and never falls through — so the host id becomes the HMAC of the empty string, the colliding one.

My probe fell back on empty instead of on unreadable. And the dbus package ships a populated /var/lib/dbus/machine-id. So in precisely the dangerous case, the probe consulted a file getHostId() would never reach, saw a healthy id, and waved the box through.

Fallback now happens on unreadable, matching getHostId() branch for branch. Verified against both real containers:

To finish the drive

Run it from a client you are signed into — your laptop — against any reachable box:

superset hosts add ubuntu@somebox --org superset --yes

That is the only missing link. Everything it does before apiKey.create is verified above against a machine that really existed, and the two calls it makes after are ordinary reads and writes this workspace simply is not permitted to make.
