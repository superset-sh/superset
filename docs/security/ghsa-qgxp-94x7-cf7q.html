01The attack

Anyone could register an OAuth client — allowUnauthenticatedClientRegistration means no session, no key, no review — and send a victim through the ordinary authorization flow. The consent screen asks the user to pick one organization and tells them, in as many words, “This application will have access to data in the selected organization.” But customAccessTokenClaims deliberately mirrored the user's entire membership list into the token's organizationIds claim, and both authorizers downstream — jwtProcedure in packages/trpc/src/trpc.ts and the relay Worker in apps/relay/src/access.ts — decide membership straight off that list and never read the consented organizationId. Asking for resource=<API url> at the token endpoint is enough to get a JWT the API verifies against its own JWKS, and there is no azp or scope check on that path. So a single consent for a throwaway org yielded a token that read environment secrets, agent credentials, hosts and cloud workspaces in every other organization the victim belonged to — for seven days, with nothing in the UI to reveal it. (The MCP path was never affected: it re-mints a one-organization token of its own.)

04The fix

One source-of-truth change. The claim shaping moved out of the better-auth config into a module that can be tested without standing up better-auth, and it now returns the consented organization and nothing else.

// packages/auth/src/lib/oauth-access-token-claims/oauth-access-token-claims.ts

export function oauthAccessTokenClaims({ referenceId, metadata }) {
  const clientName = metadata?.client_name;
  return {
    organizationId: referenceId ?? undefined,
    organizationIds: referenceId ? [referenceId] : [],
    client_name: typeof clientName === "string" ? clientName : undefined,
  };
}

The shared guard

superset is the one client that legitimately acts outside the organization its consent named — organization switch, SUPERSET_ORGANIZATION_ID and auth login --organization are all local choices made after login. Scoping the claim alone would have broken it. Its token already stands in for the user's session everywhere else (sessionFromOAuthBearer builds one from it, and protectedProcedure re-checks membership against the database), so jwtProcedure now lets that session branch resolve organizations for a first-party client and confines every other OAuth token to its consent. One predicate names the exception, replacing a private copy that already lived in the API's context:

// packages/shared/src/auth/oauth-clients/oauth-clients.ts

export const FIRST_PARTY_OAUTH_CLIENT_IDS = ["superset-cli"] as const;

export function isFirstPartyOAuthClient(azp: unknown): boolean {
  return (
    typeof azp === "string" &&
    (FIRST_PARTY_OAUTH_CLIENT_IDS as readonly string[]).includes(azp)
  );
}

azp is minted by the provider from the client id it generated at registration, and the token endpoint writes it after custom claims are spread — so a registering client cannot choose it or overwrite it, and cannot claim to be the CLI.

06Residual risk

The first-party carve-out is the soft spot. jwtProcedure still accepts any token the JWKS verifies, whatever client it was issued to; the single azp read is now the only thing separating a first-party client from a third-party one. That read is sound — the provider generates client ids and writes azp itself — but it is one check carrying weight that a broader azp/scope policy should carry.

Follow-up, not in this change: enforce azp and scope on the jwtProcedure path for all callers as defense in depth; then drop the carve-out entirely and make superset organization switch re-authorize when the stored credential is an OAuth token consented to a different organization. That last part is a behaviour change for CLI users, so it deserves its own review rather than riding along with a security patch.

  • Client registration is still unauthenticated. Out of scope here, and no longer sufficient for cross-org access on its own — but it remains the reason any attacker can reach the consent screen at all.
  • Tokens issued before this change still carry the wide claim and stay valid for up to seven days. Revoking outstanding OAuth access and refresh tokens is an operational step this change does not perform.
  • A consent-scoped token is still a real token. Within the consented organization it reads environment secrets and agent credentials exactly as before; the fix narrows reach, not authority.
  • Re-authorization follows the session's active organization, not the originally consented one. That is the intended behaviour, and it means the scope can move when the user re-consents.

07How this was verified

Everything above came from a fully local stack inside an isolated cloud workspace: Postgres, the neon-http proxy and Redis in Docker, with .env replaced by .env.local.example so only fake credentials were in play. No production database, no customer data, no real provider secret. The brief suggested a Neon branch; a branch of this project would have been a copy-on-write copy of production data, so the local stack was used instead. The sandbox also exports a production DATABASE_URL that overrides .env, so every command was explicitly pinned to the local database — that and three other sandbox traps are now written up in docs/cloud-sandbox-mismatches.md.
