Superset vs Herdr, at the command line

Herdr (YC F26) is a single-machine terminal runtime for coding agents — a tmux-grade CLI and socket API over one server's panes and sessions. Superset's CLI is a fleet-orchestration client over hosts, projects, and an org. This is what each can do that the other can't, scoped strictly to the CLI surface.

Herdr v0.8.0 Superset CLI v1.25.0 Source: --help output, all subcommands, both tools
Superset CLI

A client for a fleet-management API: workspaces, agents, and terminals across hosts and an organization, plus tasks, scheduled automations, published pages, auth, and browser-pane driving over CDP. Built for orchestrating many agents across many machines.

Herdr CLI

A client for one server's socket API: workspaces, worktrees, tabs, panes, and agent sessions on a single machine, with tmux-style attach/detach, raw key injection, and pane geometry control. Built for keeping terminals alive and directly steerable.

Reading the gaps

The eleven items above are real and mostly cheap to close individually — send-keys, a wait-for-state flag on terminals/agents, and shell completions are the highest-leverage, lowest-cost additions if the goal is scripting parity. But most of the list is the reason Herdr exists: fine-grained pane geometry, tmux-style session attach, and a self-describing socket API are a single-machine terminal multiplexer's entire job description, not a checklist Superset is behind on.

The sharper way to read it: Superset's CLI is a fleet-management client that happens to touch terminals; Herdr's CLI is a terminal multiplexer that happens to know about agents. Closing every row here would mean growing Superset's terminal primitives into a second pane-management layer next to the desktop app's own — worth doing only for specific scripting workflows that are actually blocked today (raw key injection and wait-for-state polling are the two most likely candidates), not as parity for its own sake.
