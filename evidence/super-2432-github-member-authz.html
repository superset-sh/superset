SUPER-2432 SUPER-2022 · design, open Task P1-D

Org members could read the owner’s private GitHub repositories

Reported by a customer (Hugo). Traced, confirmed, fixed, and proven with a before/after regression suite.

VERDICT: CONFIRMED STATUS: FIXED 1 DESIGN QUESTION OPEN

The attack

A Superset organization has exactly one GitHub App installation, and it is frequently installed on the owner’s personal account (accountType: "User") rather than a GitHub org. The sync job ingests every repository that installation can reach — private personal ones included — and records them against the organization. Every read path downstream then asked only “are you a member of this org?” (verifyOrgMembership / assertMember); the role column was never consulted and no share/ACL model existed for GitHub resources at all. So any invited member could enumerate the owner’s private repository inventory, pull requests, branches and collaborators — and reach the file contents two ways: create an environment over a private repo and let the sandbox clone it with the App’s installation token (the one pre-flight check was skipped precisely for members who had not connected their own GitHub account), or simply mint a gate ticket for a workspace someone else had already created, which by its own code comment hands over “terminals, git, files and the desktop.”

The fix

One shared guard — packages/trpc/src/lib/github-user/reachable-repositories.ts — answering a single question: which of this organization’s synced repositories may this caller read?

public repository → allowed (no boundary to enforce) caller connected the installation → allowed (its contents are theirs) GitHub shows it to their own account → allowed no connection · no OAuth client · refusal → DENIED

Reachability is a single call to GET /user/installations/{id}/repositories with the caller’s own user-to-server token — GitHub computes the intersection of the installation’s repositories and that account’s access itself, so it is one request per person rather than a permission probe per repository. Cached 60s per (person, installation).

Why connectedByUserId is an entitlement, not a hole

Installing the GitHub App does not create a githubUserConnections row — they are separate OAuth flows. Without this arm, the owner who connected the installation would need a second, separate connection to keep seeing their own repositories, and the fix would break the exact person it protects. The column already existed on the table and was never read by any query; this is the first thing that reads it.

Two entry points, so a new caller is safe by default rather than by remembering:

  • reachableRepositories({userId, organizationId, repositories}) — filters listings.
  • assertRepositoriesReachable({…}) — refuses with FORBIDDEN, naming the repositories, for paths acting on a named set where silently dropping a row would half-configure something.

Residual risk

1 · Empty picker for members without a GitHub connection — open, SUPER-2022

Members who have not connected their own GitHub account now see no private repositories where they previously saw the owner’s full inventory. That is the correct behaviour and the entire point of the fix, but it is a visible product change with no onboarding nudge (“Connect GitHub to see private repositories”) built. This is the one thing that should be decided before shipping. The guard is correct without it; the experience is abrupt.

2 · No creator bypass on the ticket mint

Someone who created a workspace over a repository they cannot reach — which was possible before this fix — loses access to that box. That is remediation of the existing leak rather than a regression, and it is why the check is on the checkout rather than on createdByUserId: a creator bypass would leave every pre-fix workspace a live leak.

3 · Deployments without the OAuth client

Where GH_APP_CLIENT_ID / GH_APP_CLIENT_SECRET are unset, no one can prove reachability, so only the installation’s connector sees private repositories. Fail-closed is the intended direction, but it is a config-dependent behaviour change worth knowing about before a self-hosted rollout.

4 · Up to 60s of staleness

From the reachability cache: a GitHub grant or revocation takes up to a minute to be reflected. Access granted is delayed; access revoked lingers for the same window.

Adjacent, not fixed here

Any member can still replace the org’s GitHub installation — apps/api/src/app/api/github/install/route.ts uses requireOrgMember and the callback upserts on the org-unique key, while only disconnect requires admin. Out of scope for this boundary; worth its own ticket. An install-time warning for the accountType === "User" case — an owner publishing their personal private repos to the org — also belongs with the SUPER-2022 design work.
