The attack

Every lifecycle sink resolves its commands through one function, loadSetupConfig(), which merged four config sources — and one of them was <worktreePath>/.superset/config.json, merged over the main repo's. That file is the content of whatever branch the workspace is checked out on, and .superset/config.json is tracked in git (only config.local.json is ignored). So an attacker opens a pull request against your repo containing a .superset/config.json. A maintainer opens that PR as a workspace: the branch's setup commands are joined with && and typed straight into a live PTY, unprompted. The maintainer reads the diff, decides not to merge, and deletes the workspace — and the branch's teardown is handed to spawn() with the user's own login shell and full privileges, on the very action meant to discard the untrusted code. run and cwd are steerable the same way. copySupersetConfigToWorktree() only copies the main repo's config in when the worktree has none, so a branch that ships its own keeps it intact.

The sinks

  • teardown → spawn(shell, args, { cwd: worktreePath, … }) — utils/teardown.ts:41-71, reached unprompted from procedures/delete.ts:222 and :520
  • setup → commands.join(" && ") written into a PTY — launch-command.ts:50, bootstrap-open-worktree.ts:36, WorkspaceInitEffects.tsx:135-190; queued for PR workspaces at useCreateFromPr.ts:45
  • run / cwd → procedures/query.ts:78-79 → the run terminal and its working directory

Why this is not an escaping bug

config.teardown.join(" && ") is not a classic injection sink: each array entry is a shell command line by design, so there is no metacharacter to escape — quoting them would break every legitimate config. The defect is provenance: untrusted branch content was accepted as an authoritative source of commands. The fix therefore gates who may declare lifecycle commands rather than trying to sanitize them.

The fix

loadSetupConfig() was already the single chokepoint every sink reads, so the guard went there — all nine-plus call sites, and any future one, became safe without being touched.

The shared guard

New module utils/lifecycle-trust/ holds the rule in one place:

  • LifecycleConfigSource — user-config | local-config | main-repo | worktree
  • isTrustedLifecycleSource() — trusts the first three. worktree is never trusted, because it is branch content.
  • applyLifecycleTrustBoundary() — deletes setup/teardown/run/cwd from an untrusted config, recording each drop. Deleting rather than emptying matters: the resolver merges with override.x ?? base.x, so an absent key falls back to the trusted config underneath instead of silently disabling a project's real setup script.
  • applyLocalLifecycleTrustBoundary() — same rule for the config.local.json overlay, discarding an untrusted one whole (returning null) so it cannot shadow the main repo's with nothing.

setup.ts threads a source tag through its two readers, and loadSetupConfig() became a thin wrapper over resolveLifecycleConfig(), which also returns rejected[] and logs a [lifecycle-trust] warning per dropped field.

Trust follows the path, not the filename

The first cut of this fix trusted config.local.json because .gitignore lists it. That was wrong, and was a full bypass of the boundary: a branch can git add -f the file, and once tracked, gitignore is irrelevant. Trust now follows where the file was read from, so the worktree's overlay is untrusted regardless of its name. Locked in by a regression test that fails on pre-fix code.

Residual risk — not closed

⚠ branch-controlled script bodies

The boundary stops an untrusted branch from declaring commands. It does not stop a trusted command from executing branch content. The documented pattern is "setup": ["./.superset/setup.sh"], and lifecycle commands run with cwd: worktreePath — so a pull request that rewrites setup.sh, without touching config.json at all, still gets code execution against a victim who already had that command configured. The same holds for make, npm install lifecycle scripts, docker compose up, ./gradlew.

Closing it needs user consent before running lifecycle commands against branch content they have not vouched for — a UI flow (dialog, remembered per project/branch, plus a headless policy for superset ws create --agent), not a resolver change. resolveLifecycleConfig().rejected already carries exactly what an untrusted source tried to contribute, so that flow can be built on this signal without re-plumbing anything.

Accepted as trusted

  • <mainRepoPath>/.superset/config.json — the checkout the user themselves added as a project, and the file the in-app setup-script editor writes to. Treating it as untrusted would break every first-party flow. This means cloning a hostile repo and adding it as a project is still exposed — the same case the consent flow above would cover.
  • ~/.superset/projects/<id>/config.json and the main repo's config.local.json — outside any branch, writable only locally.

Deliberate behaviour change

A branch can no longer change its own setup/teardown/run/cwd. Legitimate paths: land it on the default branch, where the main-repo config picks it up; or for a machine-local change, use .superset/config.local.json in the main repo (gitignored, trusted). Reviewers should confirm this tradeoff.
