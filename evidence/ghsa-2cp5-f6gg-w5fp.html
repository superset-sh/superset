Security advisory · Fix report

OAuth callbacks trusted the state, not the browser

GHSA-2cp5-f6gg-w5fp Confirmed · reproduced live Fixed · proved closed 9 callbacks · 7 were vulnerable branch superset/p0-2-oauth-state-binding-fix-499ab9f8

An integration connect route minted a signed OAuth state that named an organization and bound nothing to the browser holding it, so whoever finished the flow handed their grant to whoever started it. Now minting the state and binding it to the asking browser is one shared operation, and every callback refuses a state the answering request's cookie does not carry.

The attack

The signed state carries { organizationId, userId, timestamp } and an HMAC, and resolveCallback read the identity straight out of it — verifying only that the named user was still a member of the named org, which is trivially true for an attacker's own state. So an attacker signs up (a free signup auto-creates a personal org), hits a connect route for their own organization to mint a valid state, and sends the provider's authorize URL to a victim. The victim approves in their own browser, under their own session, against their own GitHub org or mailbox or Slack workspace — and the provider redirects to a callback that reads the attacker's state, writes the installation or connection row against the attacker's organization, and records the attacker as the connecting user. For GitHub that means githubInstallations lands on the attacker's org and installationTokenFor will mint tokens for the victim's repositories inside it. No signature forgery, no session theft, no provider secret — the attacker only needs a state that is genuinely theirs and a victim willing to click Approve.

How the live drive was possible without provider secrets. A throwaway Neon project (created empty, migrated from scratch, deleted after), a .env built from .env.local.example's fake placeholders, and a local stand-in for api.notion.com on 127.0.0.1. Notion is the one flow whose DB write needs a single provider call, which is why it is the one driven end to end — the vulnerable code path (resolveCallback) is shared by all nine callbacks. No production database, no real customer data, no real provider credentials.

The fix

Not a check copy-pasted into seven files. Minting a state is binding it: a single beginOAuthFlow signs the state and sets it in an HttpOnly, SameSite=Lax cookie scoped to that flow's own path, and resolveCallback takes the cookie as a required option and refuses any callback whose state the request's cookie does not carry. Every exit — the preamble's, and the route's own through exit/fail — expires that cookie, so a callback that ended early leaves no live state behind for the rest of its TTL.

// apps/api/src/lib/integrations/oauthFlow.ts

export async function beginOAuthFlow(
	options: BeginOAuthFlowOptions,
): Promise<Response> {
	const state = createSignedState(options.payload);
	const headers = new Headers({ Location: await options.authorizeUrl(state) });
	headers.append("Set-Cookie", setStateCookie(options.cookie, state));
	for (const stale of options.clear ?? []) {
		headers.append("Set-Cookie", clearStateCookie(stale));
	}
	return new Response(null, { status: 302, headers });
}

Bound by default

  • requireOrgMember no longer returns a state token at all, so a new connect route cannot mint an unbound one by accident.
  • resolveCallback's cookie option is required, so a new callback cannot resolve an identity without naming one.
  • One STATE_COOKIES registry holds every flow's cookie name and path, so the route that starts a flow and the route that finishes it cannot drift apart. A test asserts the names are unique.
  • The two routes that already did this by hand were refactored onto the same helper, so all nine callbacks share one implementation.
  • Microsoft Teams is the one two-leg flow: its consent callback mints the sign-in leg's state itself, so that redirect sets the identity cookie and retires the consent cookie in the same response (clear: [...]).

Residual risk

  • In-flight flows break once on deploy. A user mid-authorization when this ships has no state cookie and will be refused with invalid_state; retrying from the connect page works. The two pre-existing cookie names are preserved, so only the seven newly bound flows are affected, for at most the 10-minute state TTL.
  • The cookie is the binding, so it inherits cookie limits. SameSite=Lax is correct for a top-level provider redirect, but a browser that blocks the first-party cookie, or a user who completes the flow in a different browser or a private window from the one that started it, will legitimately be refused. That is the intended trade.
  • Sentry and connector app-installs are bound by the cookie alone (stateInCookieOnly) because those providers return no state of ours. Holding the cookie is the proof there; there is no second factor to cross-check against.
  • Only the Notion flow was driven end to end live. The other eight share the same resolveCallback guard and are covered by the unit tests, but their provider-specific legs were not exercised against a real provider.
  • Out of scope, unchanged: github/user/callback (a desktop-initiated flow with its own state handling) and the plugin OAuth state path were not part of this advisory and were not touched.
