The attack

Every filesystem RPC resolves through getServiceForWorkspace → createFsHostService({ rootPath }), where rootPath is the workspace's worktree path — so the workspace root is known at every call, and the only question is whether an op checks against it. Two families did not. The read ops simply never received it: listDirectory and getMetadata took no rootPath parameter at all, and readFile gated its only guard behind if (isPathWithinRoot(...)) — so a path that was obviously outside the root skipped validation, while one that merely looked inside got checked. An authenticated caller could therefore pass /home/user/.ssh/id_rsa and read it. The mutation ops failed differently: movePath and copyPath validated paths lexically via ensureWithinRoot but never physically, so a symlink committed into the repo (escape -> /outside) made <root>/escape/x pass the string check while landing outside the worktree. That escape runs both ways, and the inbound direction is the worse one: copyPath could pull a file from outside the workspace into it through the symlinked ancestor, depositing it somewhere the agent then reads over the ordinary, fully-confined read path.

The fix

Rather than patch five call sites, all paths route through one gate in packages/workspace-fs/src/fs.ts: lexical containment, then physical containment — the second half being exactly what move and copy were missing. 

async function resolveConfinedPath(
	rootPath: string,
	absolutePath: string,
	confinement: PathConfinement,
): Promise<string> {
	const targetPath = ensureWithinRoot({ rootPath, absolutePath });

	// The root's own parent is by definition outside the root, so the root can
	// only ever be validated against itself.
	const isRoot = targetPath === normalizeAbsolutePath(rootPath);
	if (confinement === "follow-final" || isRoot) {
		await assertRealpathWithinRoot(rootPath, targetPath);
	} else {
		await assertParentWithinRoot(rootPath, targetPath);
	}

	return targetPath;
}
The mode is not a security knob — both modes confine. It separates ops that act through the final path component (open, readdir) from ops that act on the component itself (lstat, rename), where only the ancestor chain can escape. Resolving the final component for those would break legitimate handling of an in-root symlink — you could no longer inspect or rename one.

Residual risk & caveats

A deliberate policy was reversed, not a missed guard. The read behaviour was documented as intentional in-code ("reads are host-wide") and pinned by passing tests named "readFile allows viewing paths outside the workspace root". The advisory overrules that, so three tests were inverted and a non-vacuous in-root counterpart added so the inverted pair cannot pass trivially. Flagged loudly because inverting tests is exactly how a real regression hides. User-visible cost: clicking a terminal link that points outside the worktree (/usr/local/bin/node, a system stack frame) no longer opens it in the file viewer.
The advisory bodies could not be read. gh api …/security-advisories/<id> returned 403 Resource not accessible by integration for all three IDs, and the list endpoint returned [] — the session token is the superset-app[bot] installation, which lacks the scope. Verification ran against the claims as stated in the task, not the reporters' own PoCs, so affected-version ranges and the rg8v duplicate determination were never read first-hand. Re-verify scope against the real advisory text before publishing fixes.
Same defect class left unfixed in deletePath. It runs ensureWithinRoot and then, when a trashItem handler is supplied, calls it before any physical check — so the trash path shares the move/copy weakness. host-service supplies no trashItem, so its RPC surface is unaffected today. Recorded rather than silently widening this change; worth a follow-up if a trash handler is ever wired up.
One unrelated pre-existing failure. The full host-service suite reports 2093 pass / 8 todo / 1 fail. The failure — health.check > serialises the current boot's stamps and the runtime in sandbox mode — was confirmed pre-existing by stashing the fix and re-running that file: identical result. It touches boot stamps in sandbox mode, not the filesystem path.
