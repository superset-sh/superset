Open **Pull requests** in the dashboard sidebar to review GitHub pull requests and GitLab merge requests from your projects. The resizable split view shows the request list on the left and the selected request's description, checks, and diff on the right. GitLab items use **Merge request**, **!IID**, and **Open in GitLab** in their details.

![The Pull requests split view: filterable list on the left, detail with rendered markdown on the right](/images/pull-requests-view.png)

## Browse and Filter

The list shows requests from the repositories behind your projects. Each row carries the repository, request number, title, author, a compact CI check summary, age, and the +added/−deleted line counts. GitLab merge requests keep their project-local `!IID` and link to the correct GitLab instance.

- **State tabs**: **All**, **Open**, or **Merged**
- **Repository**: multi-select across your projects' repos
- **Author**: filter to a specific GitHub author
- **Reviews**: review-status filter for GitHub-only selections: *No reviews*, *Review required*, *Approved review*, *Changes requested*, *Reviewed by you*, *Not reviewed by you*, *Awaiting review from you*, or *Awaiting review from you or your team*. This filter is unavailable when GitLab projects are selected
- **Search**: find PRs by title or number

Filters persist, so the view comes back the way you left it. Active filters show a count badge next to the search box.

## The Detail View

Selecting a PR opens it in the right pane, with **Summary** and **Code** tabs. Toggles at either end of the header collapse the list or the detail pane when you want more room; on narrow windows the panes stack automatically.

### Summary

The Summary tab shows the request description alongside:

- **Checks**: CI checks or GitLab pipeline jobs with their status and a link to the run. The header summarizes known states at a glance. Cancelled or unknown jobs are not shown as successful
- Review status and reviewers when the provider and project expose them; unavailable GitLab review data remains unknown
- The comment thread, with a composer for replying

![PR checks alongside the summary, with Start Workspace and Merge actions in the header](/images/pr-checks.png)

### Code

The **Code** tab is a complete diff viewer: a file tree with per-file added/deleted counts and modified/renamed markers, syntax-highlighted diffs, collapsed unmodified regions, and unified or side-by-side layouts. A **Files** dropdown jumps to any file in the changeset.

![The Code tab: file tree plus syntax-highlighted diffs](/images/pr-code-view.png)

### Comment Straight to an Agent

Select lines in the Code tab and send a comment to an agent. The agent receives the file, line range, and diff side:

- If a workspace is already linked to the PR, send it to one of its **running agent terminals**, or start a **new agent session** there
- If no workspace exists yet, Superset **creates a PR-checkout workspace** and launches the agent with your comment as its first prompt

## Actions

From the detail header:

- **Start Workspace** - check out the PR into a new workspace to run, test, or continue it. See [Workspaces](/workspaces)
- **Merge** - choose a merge method the provider and project allow. GitHub supports **Squash and merge**, **Merge commit**, and **Rebase and merge**; GitLab offers supported merge and squash choices and checks that the reviewed head has not changed
- **Close** / reopen the request
- Open the request on GitHub or GitLab

<Callout type="info">
Merging, closing, and commenting act on the real request with your provider permissions. If a GitLab merge request changes after you review it, refresh and choose Merge again.
</Callout>

In a linked workspace, use the review controls to create a request or mark a draft ready for review. GitLab discussions support replies and resolution where you have permission.

## Where PRs Come From

GitHub requests use your GitHub connection. GitLab requests are read from each project's GitLab remote using the [GitLab CLI login on its host](/tasks#gitlab-setup); GitLab.com and configured self-managed instances are supported. A successful CLI login does not set up Git clone or push credentials. Linked workspaces also show [PR status](/workspaces#pr-status) in the sidebar. For a review workflow, see the [PR feedback recipe](/recipes/pr-feedback).
