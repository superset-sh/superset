## Overview

A workspace lives on the machine that hosts its files, terminal, and ports. **Remote access** lets you reach a workspace that's hosted on a different machine, like a Mac mini under your desk, a sandbox your team shares, or a spare laptop in the office.

**Superset Relay** is a service that provides a secure way to route traffic between your different devices. There are two ways to grant a device remote access through the relay:

## Option 1: Desktop

<Callout type="warn">
Exposing your primary workstation through the relay means anything reachable by your local host service (files, terminals, agent runs) becomes reachable by clients you grant access to. The recommended setup is a **separate machine** provisioned with only the repos and credentials you intend to share. That way a misclick or compromised client can't wipe an unrelated project or leak unrelated secrets.

Use the desktop toggle when you genuinely need it on this machine. Otherwise prefer the CLI path on a dedicated host.
</Callout>

Open the desktop app and go to **Settings → Remote Access**. Flip on **Allow remote access to this device via relay**.

![Settings → Remote Access relay toggle](/images/remote-workspaces-security-toggle.png)

Enabling the toggle restarts the host service, so any running terminals on this device will be interrupted. You'll be asked to type a confirmation phrase before the change applies.

## Option 2: CLI

<Callout type="info">
See the CLI's [Getting Started](/cli/getting-started) and [Host Server](/cli/host-server) docs to get set up.
</Callout>

On the machine you want to add to your shared relay network, sign in and start the host server.

```bash
superset auth login
superset start --daemon
```

`superset start --daemon` runs a small HTTP server in the background and registers the machine with the relay so other clients in your organization can find it.

Verify it's online:

```bash
superset status
```

### Headless (sandbox, CI, or server)

On a machine with no browser to complete an interactive login, authenticate with an API key instead. Create one in **Settings → API Keys**, then export it. The CLI reads `SUPERSET_API_KEY` automatically (no `superset auth login` needed):

```bash
export SUPERSET_API_KEY=sk_live_…
superset start --daemon --org <id|slug|name>
```

Pass `--org` to choose which organization the host registers under. It's required when your key belongs to more than one organization (the CLI won't guess); with a single organization you can omit it. The host claims itself to the key's user on first registration. No desktop step required.

Observe or manage it from the same headless environment. Every `hosts`/`status` command takes the same `--org`:

```bash
superset hosts list --org <id|slug|name>
superset status --org <id|slug|name>
```

## Grant teammates access

When a host first comes online, the user who started it is the only one with access. Other members of your organization won't see it in their workspaces list until you add them.

Open **Settings → Hosts** in the desktop app, pick the host, and use **Add member** to grant teammates access. Owners can promote members to owner or remove them from the host.

![Settings → Hosts members table](/images/remote-workspaces-hosts-members.png)

## Reach a remote host from another device

On any other device signed into the same organization, open the desktop app's **Workspaces** list. Use the **Device** filter in the top right to pick a remote host:

- **This device**: workspaces on the machine you're using now
- **Other devices**: each remote host that has opted in, listed by name with an online indicator

![Device filter in the workspaces list](/images/remote-workspaces-device-filter.png)

Pick a remote host to see the workspaces hosted there. Open one and you get the full Superset experience (terminals, agent runs, the diff viewer) proxied through the relay to the host machine.

### Ports on a remote host

The ports sidebar shows ports listening **on the remote host**. When you select a remote workspace, the desktop app forwards each of its ports to the same port number on your machine, so `localhost:3000` reaches the dev server on the host. All traffic for a workspace shares one tunnel, established when you select the workspace; every connection reuses it. When you select another workspace, the app stops those forwards and starts the new workspace's forwards.

Only ports that the workspace started are forwarded. Other services on the host stay unreachable.

If a local process already uses the port, the row shows **local port busy** and offers two actions: stop the local process (only when a Superset workspace started it) or **Use another port**, which maps the remote port to a free local port and shows the mapping, for example `3000 → localhost:54321`.

The remote server sees each forwarded connection as coming from its own loopback address — there is no real client IP. Only TCP is carried; anything UDP (WebRTC media, mDNS) does not ride the forward.

Forwarding needs a host on the current relay running host-service 1.26 or newer. For a host you reach some other way, [forward a port yourself](/ports#forward-a-port-yourself) with SSH or Tailscale.

Forwarded traffic passes through the Superset relay, like terminal traffic does. A browser talking to a forwarded dev server sends whatever it normally would — cookies, auth headers, query strings — so treat a forwarded port like the remote service it reaches, not like localhost.

## Turning access off

- **Desktop**: flip the toggle in **Settings → Remote Access** back off. The host service restarts and stops accepting relay traffic.
- **CLI**: run `superset stop` on the host machine.

In both cases, in-flight terminals and host-backed work on that machine are interrupted.
