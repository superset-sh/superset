Proposal

Branch autonaming drops the custom prefix. Let's fix the code path and merge the two settings that control it.

Autonaming and branch prefix live in different settings screens and don't talk to each other. When an AI-generated name lands, it silently overwrites the prefix a user configured — moments after the workspace correctly had it.

Author Kiet Ho Area Workspace creation · Desktop settings Status For discussion

The bug

A workspace's branch prefix (none / github / author / custom) is resolved correctly at the moment a workspace is created. But when AI autonaming finishes a few seconds later and renames the branch to something better than the placeholder, the prefix isn't reapplied — it's just gone.

1
Workspace created with placeholder branch
resolveProjectBranchPrefix runs, prefix applies correctly → kiet/quick-brown-fox
2
AI naming call runs in the background
The launch agent reads the prompt and proposes a better name: fix-login-timeout
3
applyGeneratedWorkspaceNames renames the branch — without the prefix
git branch -m uses the AI name raw → kiet/quick-brown-fox becomes fix-login-timeout

The live branch-name preview shown while typing a prompt has the same gap: workspaces.ts's generateBranchName procedure never calls resolveProjectBranchPrefix at all, unlike the create procedure right next to it. What the user sees while typing already doesn't match what they'll briefly get.

Notably, this already works elsewhere in the codebase

The legacy desktop-local naming path (apps/desktop/.../generate-branch-name.ts) threads resolveBranchPrefix into its dedupe step correctly. The regression is isolated to the newer host-service path — the one the app is actively migrating onto — which makes it worth fixing before that migration finishes and the correct behavior disappears entirely.

Why it's easy to miss

Because the two settings that govern this outcome sit in different places, with no visible link between them:

  • Branch prefix mode + custom string — a global "Git & worktrees" settings page, with a per-project override buried in that project's own settings page.
  • Naming instructions (what steers the AI's autoname style) — a separate section on the same per-project settings page, not adjacent to the prefix override.

There's also no toggle anywhere to turn autonaming off. It's implicit: it fires whenever a user hasn't hand-edited the branch name field. A user configuring "how my branches get prefixed" has no reason to know a second, disconnected control shapes what autonaming will produce — or that the prefix won't survive it.

Proposed fix

  1. 1
    Apply the resolved prefix in both host-service code paths

    Call resolveProjectBranchPrefix in the live-preview generateBranchName procedure, and — the important one — reapply it inside applyGeneratedWorkspaceNames after the AI/derived name comes back, instead of using that name raw in the git branch -m. This brings host-service to parity with what the legacy desktop path already does correctly.

  2. 2
    Put both settings in one section

    Merge the project settings page's branch-prefix override and "Naming instructions" into a single "Branch naming" section, so configuring one surfaces the other instead of splitting them across a global page and a distant per-project block.

  3. 3
    Show a live example in that section

    A one-line preview — "with your current settings, a workspace from this prompt would be named kiet/fix-login-timeout" — so the prefix-plus-autoname interaction is visible before creating a workspace, not discovered after the fact.

Open questions

  • Once V1 (legacy desktop) settings are retired, does the fix in host-service become the only implementation to maintain, or is a shared resolver worth extracting now?
