# Internationalization Strategy

Research + plan, 2026-08-26. Covers library choice, architecture, the two contract
changes that must land first, enforcement, translation pipeline, and migration
sequencing across desktop, web, mobile, marketing, docs, and email.

## TL;DR

- The repo is a true i18n greenfield: zero i18n libraries, zero catalogs, every
  user-facing string is hardcoded English, and ~37 `Intl.*` call sites pin `"en-US"`.
- Total scope is roughly **4,000-5,500 messages**, dominated by desktop
  (~2,500-3,500, including 550 toast call sites and Electron main-process menus).
- **Recommended stack: Lingui 6** with explicit IDs + default messages, `.po`
  catalogs in a new `packages/i18n`, compiled per-app (SWC plugin for Next, Babel
  plugin for electron-vite, Metro transformer for Expo). Runner-up: i18next.
- Two contract changes must land before the bulk migration (Phase 4+); the
  Phase 0 spike's handful of pilot strings does not depend on them:
  1. a persisted locale (new `locale` column on the Postgres user table + a
     `language` setting in local-db/settings registry for desktop),
  2. a machine-readable tRPC error contract (171 `TRPCError` sites whose English
     `message` is rendered verbatim by 104 client call sites today).
- Enforcement is repo-idiomatic: `lingui extract` hooked on `pretypecheck`,
  `lingui compile --strict` as a step in the existing CI `lint` job, and an
  ast-grep **ratchet test** for hardcoded JSX strings (we use Biome, not ESLint,
  so lint-plugin approaches don't apply).
- Translation pipeline: LLM translation in CI with a glossary, human spot review
  for high-stakes copy. Roll out locale-by-locale behind a PostHog payload flag
  (same pattern as `AUTOMATION_EVENT_TRIGGERS`).
- Docs (fumadocs has native i18n, `useI18n` already imported) and marketing MDX
  content (~116 files) are separate editorial tracks. `apps/admin` is skipped.

## 1. Current state (survey findings)

### No i18n exists anywhere

- No i18n library in `bun.lock` (checked i18next, next-intl, lingui, formatjs,
  react-intl, paraglide/inlang, and friends).
- No `locales/`, `messages/`, or catalog files of any format. No `i18n` config in
  any `next.config`. No `Accept-Language` handling anywhere, client or server.
- The single adjacent dependency: `expo-localization@57.0.1` is installed and
  registered as a plugin (`apps/mobile/app.config.ts:63`) but never imported.
  Device locale detection on mobile is free.

### How strings are written today

- 100% hardcoded English inline in TSX/TS. No copy layer.
- **Toasts are the single largest concentrated surface**: 550 `toast.*` call
  sites in desktop (114 with template literals that need ICU interpolation),
  14 in web. Mobile uses `Alert.alert` instead.
- **Electron main process has its own string surface** a renderer runtime can't
  reach: ~76 menu labels (`apps/desktop/src/main/lib/menu.ts`), tray
  (`src/main/lib/tray/index.ts`), dialogs, OS notifications. Needs a plain-JS
  catalog in main + locale over IPC + menu rebuild on language change.
- Structured registries that are ideal pilot targets because they're already
  data-shaped: hotkeys (36 descriptions, `renderer/hotkeys/registry.ts`),
  command palette (57 strings, `renderer/commandPalette/`), CLI settings
  descriptions (`packages/cli/src/lib/settings/registry.ts`).
- **Server-side user-visible strings**: 171 `new TRPCError` sites with English
  messages; 104 client sites render `error.message` straight into a toast.
  19 React Email templates in `packages/email`. Slack integration blocks in
  `apps/api`. No push notifications exist.

### Formatting

- date-fns 4 everywhere (no dayjs/luxon/moment). 62 `toLocale*` sites, 37
  `Intl.*` sites, almost all pinned to `"en-US"` (worst offenders:
  `packages/ui/src/components/ai-elements/context.tsx` with 8 instances and its
  near-verbatim mobile fork with 10).
- Relative time is English-locked (`formatDistanceToNowStrict` with no locale).
- 37 instances of the `${n === 1 ? "" : "s"}` plural hack.
- One correct pattern already exists to generalize: `packages/shared/src/rrule.ts`
  threads a `locale` param into `Intl.DateTimeFormat`.

### Infrastructure facts that shape the plan

- Shared packages export **raw TS source** via subpath exports; consumers
  transpile. An i18n package needs no build step, and Lingui macros in shared
  packages get compiled by each consuming app's own transform pipeline.
- Codegen convention is `pre<task>` hooks, not turbo tasks
  (`apps/desktop/package.json` `pretypecheck` runs icon + route codegen), so CI
  typecheck catches drift for free. i18n extraction should follow this exactly.
- **Lint is Biome 2.4, not ESLint.** No plugin API for custom rules. The repo's
  precedent for custom enforcement is ratchet tests (the `no-*-blocking` tests
  referenced in `biome.jsonc:31`). `@ast-grep/napi` is already a desktop dep.
- Vale prose linting already runs in CI against a hand-maintained marketing file
  list; pointing Vale at the English catalog would replace that list with one
  canonical source.
- Feature flags are typed in `packages/shared/src/constants.ts` (`FEATURE_FLAGS`)
  and payload flags are already used for staged capability rollout
  (`AUTOMATION_EVENT_TRIGGERS`).

## 2. Library decision

### Constraint that decides it

One shared catalog across Electron+Vite, Next.js App Router (RSC), and Expo.
As of August 2026 only two libraries genuinely support all three:

| | Lingui 6 | i18next / react-i18next |
|---|---|---|
| Weekly downloads | ~1-1.5M | 15-21M |
| ICU MessageFormat | Native | Via `i18next-icu` plugin |
| Runtime size | ~5KB | Largest of the group |
| Extraction | Compiler-driven (`lingui extract`), dead keys impossible | Bolt-on (`i18next-parser`), drift is team discipline |
| Type safety | Macros are compile-time; `compile --strict` gates CI | Good key typing, but ICU plugin breaks typed interpolation args |
| Next.js RSC | Documented pattern, more manual than next-intl | Via next-i18next v16 or manual |
| Expo | Official Metro transformer | Works |
| Electron main | `@lingui/core` plain JS | `i18next` plain JS |

Ruled out: **next-intl** (best-in-class for Next, and its `use-intl` core
nominally lists React Native, but in practice interpolation and plurals break
on Hermes, the RN issues sit untriaged for a year+ (amannn/next-intl issues
957 and 1649, where even the FormatJS polyfill did not fix it), and it ships no
extraction tooling, which is the maintainability machinery this plan is built
on; using it web-only means two stacks). **Paraglide** (no RN support).
**react-intl** has a weak RSC story and momentum has moved elsewhere.

### Recommendation: Lingui 6

Maintainability is the deciding axis, and Lingui's model makes the two failure
modes of key-based systems structurally impossible: orphaned keys (extraction is
compiler-driven from source) and missing translations reaching production
(`lingui compile --strict` fails CI). The runtime is small enough to ship in the
Electron main process and mobile without thought.

Use **explicit IDs plus default messages** in macros:

```tsx
t({ id: "workspace.open.terminalFailed", message: "Workspace opened, but terminal failed to start." })
<Trans id="settings.appearance.title">Appearance</Trans>
```

This keeps stable, context-rich keys (translations survive English copy edits)
while retaining automated extract/prune. It is the workflow large Lingui teams
converge on and defuses the standard source-text-as-key criticism.

Accepted costs, stated plainly:

- Smaller community than i18next. Mitigation: Lingui 6.0 shipped April 2026,
  actively maintained, and `.po` is a portable format if we ever migrate.
- Next.js SWC plugin version pinning is a known friction point (SWC plugin ABI
  tracks Next versions). Mitigation: pin exact versions, and the Babel fallback
  exists.
- RSC wiring is more manual than next-intl (locale segment + `setI18n()` per
  page/layout). One-time setup cost, mostly in marketing/docs/web.

Fallback: if a spike (Phase 0) hits blocking friction with electron-vite, Next 16
SWC, or Expo SDK 57 Metro, switch to i18next + ICU JSON catalogs with the same
package layout and the same enforcement story. The architecture below is
library-portable by design; the catalog format and provider placement don't
change.

## 3. Architecture

### `packages/i18n` (new)

Follows the house convention: subpath exports pointing at `src/*.ts`, no build.

```text
packages/i18n/
├── package.json          # exports: ".", "./react", "./server", "./locales/*"
├── lingui.config.ts      # single config, catalogs per locale, sweeps all apps + packages
├── src/
│   ├── index.ts          # i18n instance factory, locale list, types
│   ├── locales.ts        # SUPPORTED_LOCALES, DEFAULT_LOCALE, rtl set
│   ├── format/           # locale-aware formatters (see §6)
│   └── react.tsx         # shared I18nProvider wrapper
└── locales/
    ├── en/messages.po    # source of truth, English
    ├── de/messages.po
    └── ...
```

One catalog set, not per-app catalogs. Per-app splitting is a bundle-size
optimization we can add later via Lingui's `catalogs` config if marketing bundle
analysis demands it; starting split adds coordination cost for no current gain.

### Per-app wiring

- **Desktop renderer**: `@lingui/babel-plugin-lingui-macro` in
  `electron.vite.config.ts`. `I18nProvider` inserted between
  `ElectronTRPCProvider` and `AuthProvider` in
  `apps/desktop/src/renderer/routes/-layout.tsx` (inside tRPC so it can read the
  persisted setting, outside auth/toasts/notices so those are translatable).
- **Desktop main**: `@lingui/core` directly (no React). Locale resolved at
  startup (setting, else `app.getPreferredSystemLanguages()` through
  `resolveLocale()`), pushed to renderer via IPC, menu
  and tray rebuilt with `Menu.setApplicationMenu()` on change.
- **Next.js apps (web, marketing, docs)**: `[lang]` route segment where
  localized routing is wanted (marketing, docs), cookie/user-preference locale
  for the logged-in web app. SWC plugin, `setI18n()` in layouts/pages per the
  official RSC pattern, prerender all locales via `generateStaticParams` on
  marketing/docs.
- **Mobile**: official Lingui Metro transformer compiles `.po` on the fly.
  `expo-localization` for device locale, re-read on `AppState` change.
  `I18nProvider` wraps `ThemeProvider` in
  `apps/mobile/screens/RootLayout/RootLayout.tsx` (above the `isPending` gate so
  loading/auth screens are localized). Declare `supportedLocales` in
  `app.config.ts` (iOS requires CFBundleLocalizations). **Hermes needs
  polyfills**: `@formatjs/intl-pluralrules` and `@formatjs/intl-locale` at
  minimum (Hermes still lacks PluralRules in 2026; ICU plurals depend on it).
- **Emails** (`packages/email`): templates take a `locale` prop, rendered
  server-side with `@lingui/core`. Locale comes from the stored user preference,
  never a request header (email sending is async).
- **CLI**: out of scope for v1 (English is fine for a dev tool CLI), but the
  settings registry descriptions flow into the desktop UI, so those strings get
  keys anyway.

## 4. Prerequisite contract change A: locale persistence

There are four settings stores and none has a locale field. Add:

1. **Postgres** (`packages/db/src/schema/auth.ts`): `locale` column on the user
   table, nullable (null = auto-detect). Unblocks web SSR, emails, and mobile in
   one migration. Follow `.agents/skills/db-migrations/SKILL.md`.
2. **Desktop local-db** (`packages/local-db/src/schema/schema.ts` `settings`
   table): `language` column + entry in
   `packages/cli/src/lib/settings/registry.ts` (gets CLI get/set + validation
   for free; `registry-coverage.test.ts` enforces completeness). UI control in
   the settings appearance section next to `ThemeSection`.
3. **Sync story**: desktop writes through to the Postgres `locale` on change
   when signed in (so emails match the app language); local value wins on the
   desktop UI. Accept independent settings when signed out.

Resolution precedence everywhere: explicit user setting > OS/browser locale >
`en`. First-load inference is implemented in `@superset/i18n`
(`inferLocale()` / `resolveLocale()`): desktop main uses
`app.getPreferredSystemLanguages()`, the renderer and web use
`navigator.languages`, mobile passes `expo-localization` `getLocales()`. So a
user whose OS is set to a supported language gets it with zero configuration.

On top of inference, onboarding gets an **optional language step**: a picker
pre-selected to the inferred locale, shown only when the `LANGUAGES` payload
flag lists more than one locale (a picker with one option is noise). Skipping
it keeps inference; choosing writes the persisted setting. The settings
appearance section remains the way to change it later.

## 5. Prerequisite contract change B: tRPC errors

The single hardest piece, and it must precede extraction because it changes the
client contract that 104 call sites depend on.

- Add a typed error payload: every user-facing `TRPCError` gains
  `cause: { i18nKey: string, params?: Record<string, string | number> }`
  (or a custom error subclass with a helper: `userError("org.lastOwner")`).
  English `message` stays populated as the fallback and for logs.
- **Translate client-side** (the client knows the locale; the server never needs
  `Accept-Language` threading and cached responses stay locale-free).
- **Serialize the payload explicitly**: tRPC does not serialize
  `TRPCError.cause` to the client by default. The router's `errorFormatter`
  must copy `i18nKey`/`params` into `shape.data`, with a round-trip test
  proving the client sees them before `errorMessage()` relies on it.
- Add one shared render helper, `errorMessage(error)`: resolves `i18nKey` from
  the catalog, falls back to `error.message`, replaces the raw
  `toast.error(e.message)` pattern at all 104 sites. This helper lands first and
  is migrated mechanically; keys are then added server-side incrementally.
- Non-user-facing internal errors keep plain messages; only the ~171 surfaced
  ones get keys.

## 6. Formatting layer (independent, land early)

A small `@superset/i18n/format` module wrapping `Intl` with the active locale,
replacing hardcoded `"en-US"`:

- `formatNumber`, `formatCurrency`, `formatDate`, `formatDateTime`,
  `formatRelativeTime` (Intl.RelativeTimeFormat instead of English-locked
  date-fns `formatDistanceToNow`), `formatTokens` (moves and localizes
  `packages/shared/src/format-tokens.ts`, whose T/B/M/K suffixes are
  English-only).
- Generalize the pattern already correct in `packages/shared/src/rrule.ts`.
- Keep `"en-CA"`/`"en-US"` at the machine-readable date-key sites (correct as-is).
- This is ~37 mechanical call-site swaps, delivers visible correctness before
  any translation exists, and is worth doing even if translation stalls.

## 7. Enforcement (the maintainability core)

- **Extraction in `pretypecheck`**: `lingui extract` wired the same way as
  `generate:icons`/`generate:routes`. Catalog drift becomes a CI typecheck
  failure with zero new CI jobs.
- **`lingui compile --strict` as a step in the existing `lint` CI job** (a
  standalone job would pay a full `bun install`; the repo already has 7).
  Missing translations for enabled locales fail CI.
- **Hardcoded-string ratchet test**, not a lint rule: Biome has no plugin API,
  and introducing ESLint for one rule is not worth it. Write a `bun test` using
  `@ast-grep/napi` that finds JSX text literals and translatable string props,
  checked against a committed allowlist that may only shrink. Same shape as the
  existing `no-*-blocking` ratchet tests. Start it in report-only mode during
  bulk migration, flip to enforcing per-directory as directories complete.
- **Vale on the English catalog**: point the existing marketing Vale setup at
  `locales/en/messages.po` so product copy gets the same prose rules, replacing
  the hand-maintained TSX file list over time.
- **Glossary file** (`packages/i18n/glossary.md`): terms never translated
  (Superset, workspace?, agent names, CLI commands, keyboard keys) plus per-term
  guidance. Input to both human reviewers and the LLM pipeline.

## 8. Translation pipeline

Recommendation: **LLM translation in CI, human spot review, no TMS initially.**

- On merge to main, a CI step (Lingo.dev's action, or a homegrown script against
  our own Anthropic key, which we should prefer since translation-with-glossary
  is exactly what we build agents for) fills untranslated entries in each
  enabled locale's `.po`, opening a PR rather than committing directly.
- The glossary and per-message context comments ride along in the prompt.
- Human review: native-speaker spot checks per release for product UI; full
  human review reserved for marketing/legal copy.
- Revisit a TMS (Crowdin is the fit if ever) only when external human
  translators enter the picture. i18n-ally is unmaintained; inlang Sherlock is
  the editor-tooling choice if we want in-IDE translation preview.

## 9. Rollout

- `FEATURE_FLAGS.LANGUAGES` payload flag returning the enabled locale list
  (`["en"]` → `["en", "de"]` ...), consumed by the language setting UI. Ships
  locales without a release, mirrors `AUTOMATION_EVENT_TRIGGERS`, and follows
  the `NEW_WORKSPACE_SCREEN` doc-comment pattern (internal override flag to
  avoid contaminating exposure).
- First target locale: pick one with real demand signal before committing
  (check PostHog OS-locale distribution and support-ticket languages;
  candidates: ja, zh, de, pt-BR). The infra work is locale-count-independent.
- Marketing/docs localized routes (`/de/...`) ship per-locale only when that
  locale's content is actually translated; UI chrome first, MDX content later.

## 10. Migration sequencing

Phases are independently shippable; each ends green with English-only behavior
unchanged.

- **Phase 0, spike (small)**: `packages/i18n` + Lingui wired into all five build
  pipelines (electron-vite renderer + main, Next SWC x3, Metro) with ~5 strings
  each, extraction + strict compile in CI. This validates the library decision;
  the i18next fallback triggers here or never.

  **Status: implemented on this branch (2026-08-26).** Findings:
  - Lingui 6 requires the `@lingui/format-po` formatter package (string
    `format: "po"` config was removed); `lineNumbers: false` keeps the CI
    drift diff free of line-number churn.
  - `@lingui/swc-plugin@6.6.0` works under Next 16.2 / Turbopack (docs app
    builds and prerenders the macro-using Sidebar). No version-table friction
    at these versions; keep the lockstep pin.
  - The extractor picks up plain `i18n._({ id, message })` descriptor calls,
    so **Electron main needs no Babel plugin**: tray strings live in the same
    catalog with zero build changes to the main pipeline.
  - First-load locale inference is in: `inferLocale()` (navigator.languages),
    `app.getPreferredSystemLanguages()` in desktop main,
    `expo-localization` `getLocales()` on mobile.
  - The Babel macro plugin and Metro discover Lingui config by upward search
    from the app's cwd, which never reaches `packages/i18n`. Fix: a root
    `lingui.config.ts` that re-exports the real config. Without it both the
    desktop and mobile builds fail with "No Lingui config found".
  - Any app importing `@lingui/core/macro` needs `@lingui/core` as a direct
    dependency (isolated linker): builds pass anyway because macros compile
    away, but tsc fails on the missing types.
  - `apps/web` and `apps/marketing` do not build locally with or without these
    changes (env: `neon()` connection string, t3-env validation at page-data
    collection); they build on Vercel. Docs is the local Next build proof.
  - The i18next fallback was not needed.
- **Phase 1, contracts (medium)**: locale persistence (§4), tRPC error contract
  + `errorMessage()` helper (§5), formatting layer + 37 call-site swaps (§6).
- **Phase 2, dedupe before extraction (medium)**: the v1/v2 desktop UI
  duplication (`src/renderer/screens/main/` vs
  `routes/_authenticated/_dashboard/v2-workspace/`) and the
  `ai-elements/context.tsx` mobile fork mean a big slice of strings exists
  twice. Dedupe what's cheap, and scope extraction to v2 surfaces where v1 is
  scheduled for deletion (v1 sunset is already in flight). Do not translate v1.
- **Phase 3, pilots (small)**: hotkey registry, command palette, settings
  registry descriptions. Data-shaped, proves the pipeline without JSX churn.
- **Phase 4, desktop bulk (large, parallelizable)**: toasts (550) → settings
  tree → main-process menus/tray/dialogs → remaining renderer surfaces.
  Directory-by-directory, flipping the ratchet as each completes. This is
  ideal fan-out work for parallel agent workspaces.
- **Phase 5, web + mobile + email (medium)**: web app (~350-500 messages),
  mobile (~400-600, plus `Alert.alert` and `app.config.ts` iOS permission
  strings), the 19 email templates.
- **Phase 6, public sites (separate editorial track)**: docs first (fumadocs
  native i18n, `useI18n` already imported, cheapest win), then marketing UI
  chrome, then marketing MDX content per-locale on demand.

Out of scope: `apps/admin` (internal), `apps/streams` (empty stub), CLI output,
RTL locales (see below).

## 11. Landmines and risks

- **CDN `Vary` header**: `apps/marketing/src/proxy.ts` already negotiates on
  `Accept` + `User-Agent` and sets `Vary` accordingly. Any `Accept-Language`
  negotiation must extend `Vary` or the CDN cross-serves locales. Preferred
  mitigation: path-prefix locales on marketing/docs (no header negotiation
  except a redirect on `/`), keeping cached pages locale-keyed by URL.
- **Locale-unaware edge slug lists**: the hardcoded `CATEGORY_SLUGS` /
  `PAGE_SLUGS` / `MARKDOWN_ROUTES` in the marketing proxy, plus hand-written
  `redirects()` in marketing and docs next configs, all need locale-prefix
  handling when localized routes ship.
- **`dir="rtl"` truncation hacks**: two components abuse `dir="rtl"` to
  right-truncate paths (`ChangesFoldersView/.../FolderHeader.tsx`,
  `ChangesView/.../FolderRow.tsx`). Under a real RTL locale they invert. RTL is
  explicitly deferred, but fix these two with CSS (`direction` scoped to the
  path span + bidi isolation) whenever touched, and the codebase's universal
  `ml-`/`pl-`/`left-` Tailwind usage means RTL would be a dedicated project
  (logical properties migration + `I18nManager.forceRTL` restart gotcha on RN).
- **Next SWC plugin pinning**: Lingui's SWC plugin must be version-matched to
  Next; pin exactly and note it in the upgrade runbook. This is Lingui's most
  common community complaint (e.g. js-lingui#2423: swc-plugin 5.10.1 crashed
  Next 16.0 Turbopack at startup when middleware was present; closed). Spike
  verified 6.6.0 + Next 16.2.11: production build compiles `proxy.ts` and the
  dev server boots clean. Upstream, swc_core@47+ made wasm plugin ABIs
  compatible across more @swc/core versions, so this pain is shrinking.
- **Hermes Intl gaps**: PluralRules/Locale polyfills are table stakes on mobile
  regardless of library choice.
- **Marketing `ignoreBuildErrors: true`**: type-level catalog errors in
  marketing won't fail the Next build, only the CI typecheck job. Acceptable,
  just know the failure surfaces in the typecheck job.
- **Search/keywords**: command-palette `keywords` must be translated while
  keeping English aliases searchable (index both).
