01 The shape of the change

Every first-party integration — Google, Linear, Slack, Notion, Sentry, Microsoft Teams, GitHub — used to authenticate twice: once as an org-scoped integration_connections row behind a hand-written connect/callback route pair, and again as a user-scoped plugin_connections row behind a second, generic-but-separate OAuth pipeline. This diff does not touch triggers, webhooks, or the MCP dispatch path yet — it fuses the auth plane only, one table and one route pair standing in for both.

Two auth planes, seven duplicated route pairs → one table, one registry, one route pair, five consumers.

The merge is additive at the edges, subtractive in the middle: every provider-specific webhook handler, sync job, and trigger matcher named in the earlier design proposal is untouched in this diff — syncMailbox.ts, processDelivery.ts, jobs/renew-watches all still exist and still do what they did. What changed under them is where a token comes from: connections instead of integration_connections, resolved through packages/trpc/src/lib/connectors instead of a per-provider helper.

03 What got retired outright

Three things disappear rather than move, because the merged table makes them redundant:

  • Per-plugin OAuth config. Every plugin.json's hand-written auth: [...] block — authorization URL, token URL, scopes, identity probe, bind spec — is gone. That configuration now lives once, in connectors.json, keyed by the same slug the manifest references.
  • The plugin-only OAuth implementation. router/plugins/oauth.ts (433 lines) and its test file are deleted outright, not refactored — the generic connect/callback pair under connectors replaces what it did for every provider at once.
  • Two parallel connection UIs. Desktop's PluginConnections and its usePluginConnections hook are gone; ConnectorSection is the one component both the plugin detail page and the trigger editor now mount.

04 Where this sits on the roadmap

The design proposal committed to this branch (plans/20260909-one-plugin-surface.html) lays out four phases. Reading the diff against it:

1
Connections
merged

One connections table, backfilled indexes for org vs. user scope, one revoke path. This diff, essentially in full.

2
One server ABI
not started

Stateless MCP dispatch collapsing remote and bundled plugin servers behind one handle() function. dispatch.ts is touched only incidentally here, not restructured.

3
Discovery-first auth
partial

discovery.ts (RFC 9728) and client-identity.ts (dynamic client registration) both moved into lib/connectors and are wired into the new callback route. legacyOauth as a distinct manifest shape, and the RFC 9207 iss check called out as missing, aren't visibly addressed yet.

4
Events
not started

Generic ingress, generic trigger matcher, attributes-based filters. Every webhook route (gmail/push, linear/webhook, notion/webhook, sentry/webhook, Teams subscriptions) keeps its own provider-specific verify-and-normalize logic in this diff — only its token source changed.

05 Still open

From the proposal's blocker list (B1–B8), the two that this diff's scope leaves untouched and that later phases will have to answer:

B2
Audience-bound tokens

A connection minted through connectors/callback for, say, Linear's MCP server is not automatically valid against api.linear.app/graphql. Product code that still calls provider REST/GraphQL APIs directly — getLinearClient(), Teams' Graph calls — needs the credentials-per-resource design from §05 of the proposal before this can be relied on universally. Not yet visible in the diff.

B1
Webhook lifecycle stays hand-rolled

Google's watch renewal (jobs/renew-watches), Notion and Teams' per-workspace registration are still bespoke cron jobs against the old per-provider shape, just now reading tokens from connections. The manifest-driven events.lifecycle block from Phase 4 would fold these into one shared cron; until then, each stays a distinct thing to keep renewing correctly.
