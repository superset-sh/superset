Plan · Slack integration · v13

Superset in Slack: a teammate in the channel, not a bot you summon

Reads every message, speaks only when it should. Turns a thread into a working session on a real workspace and agent. Acts as the person who asked, with their Linear and GitHub. Remembers per channel.

v13 · 2026-09-08 · branch lace-scene · author: Claude for Avi

Changed from v1
  • Participation follows Claude Tag's rules: no per-message classifier, four outcomes, back-off, engagement memory.
  • A thread is a working session on a Superset workspace plus agent, with mid-task follow-ups queued.
  • Tool safety is tiered with an Approve button, not a flat allowlist.
  • Bug fixes from the code review are unchanged and still Phase 0.

00The model

It joins the conversation

Replies in threads it's in, answers when it's talked about, stays quiet otherwise.

It uses your integrations

Linear, GitHub and the rest come from the asker's own plugin connections.

It remembers

Per-thread transcript and entity log; per-channel memory anyone can edit.

Channel-wide: "@Superset only respond here when mentioned" flips the channel setting.
quieted · thread or channel
  • Respond automatically is per channel, default on. Change it by asking in the channel, in App Home, or as an admin.
  • Quiet a thread by replying "only respond when I mention you".
  • Back-off: after ~100 channel messages with no reply from the agent, it stops reading until the next mention.
  • Engagement memory: whether people act on unprompted replies is recorded; ignored channels get fewer.
  • Its name is not a trigger; being addressed is. "superset, did #7331 ship?" and "have superset file that" are addressed to it and get a reply without an @. "the superset invoice came through" is not, and gets nothing. The channel session reads intent from the whole message, not a keyword. When respond-automatically is off, only an @ gets through.
  • Bots are context, never a trigger. "@Superset triage this" under an alert is how to act on one.

03A thread is a working session

  • Two shapes. Tools but no code: the existing loop with the transcript replayed. Code: workspaces_create with agents, and the thread becomes that agent's conversation.
  • Where it runs. Cloud sandbox by default for channel threads, the author's host for DMs and on request, a pinned runner host per channel for teams that want one. The reasoning is below. Decision 1.
  • Follow-ups arrive without a mention. Mid-turn they're queued; on resume the thread is back-read since last context.
  • On a host, delivery reuses page-watch. Page comments already reach a running agent this way: host-service keeps a watch keyed by workspace, terminal and agent, polls for new items, holds them while the agent is mid-turn, and pastes a prompt into the PTY. A Slack thread gets the same watch, assigned by the API when it spawns the agent instead of by the CLI on publish. If the terminal is gone, the API relaunches the agent in the same workspace with resume and reassigns. Replies flow back the way this page's comments do: the agent calls the CLI, or the API posts on the agent's turn-end event.
  • Progress is a checklist edited in place, streamed. Typing status under the message, no "Thinking..." placeholder.
  • Completion callback: an agent spawned from Slack reports back into the thread. Shipped as a poll (PR D): the API asks the host over the relay, backing off 30s → 5min, until the agent's first turn ends or 24h pass. The host pushes nothing to the API today and a callback would ship with the desktop, so the poll is what works on every installed version. Later: a host→API turn-end event, tagged with the Slack origin at launch, replaces the trigger. The launch record and the completion post stay as they are; only the poll is deleted. Do it when the turn-end event is wanted for something else too (the PR-opened post in Phase 3, or the desktop's own status), and keep the poll for hosts on older versions.
  • !restart archives the session and starts fresh from the thread.

The best of each, and the pattern to move toward

This is the pattern to move toward. Claude Tag's conversational contract is the baseline, because it is the only one of the five that feels like a teammate rather than a tool. Superset adds the two things it structurally can't: the result lands in a workspace you can open in the desktop, and irreversible actions wait for a button. The other borrowings (streamed replies, queued follow-ups, dropdown clarification, signed completion callbacks) are how the baseline gets built without re-learning what the others already learned.

Three ways Superset could answer it

My pick: C. Cloud is the channel default, not the fallback.

  • Shared thread, shared compute. A channel thread can't die when one laptop closes.
  • Channel text is untrusted. Don't run it on a personal machine with full credentials.
  • Keep the Superset edge. The cloud workspace shows in the sidebar; open it on your machine.
  • DMs stay personal. Your host, your connections, your worktrees.
  • Runner host for teams that want one. Pin a channel to an always-on box. The Cyrus case, one setting.
  • Files survive, unlike Claude Tag. Needs an idle policy so it doesn't cost forever.

Cloud has to clear these first (open items in the Sandboxes project, a Phase 3 dependency):

  • idle stop, TTL, or per-org quota
  • delete wired to cloudWorkspace.delete
  • per-org model credentials instead of ours
  • GitHub token out of .git/config
  • host-service version handshake so old sandboxes fail clearly

Until then, Phase 1 runs mentions and DMs on the author's host, which works today. Channel working sessions wait rather than ship on a fallback.

  • MCP or CLI? Both, by where the code runs. The channel session and chat-shaped working sessions run inside the API, so they use the in-memory MCP client that exists today: in-process, no subprocess, auth context injected, no binary in the serverless bundle. A code-shaped working session is a Claude Code agent in a workspace, and it uses the superset CLI and installed plugins like any other agent on a host or sandbox. Both paths call the same tRPC router, so a tool added once shows up in both.
  • Linear and GitHub plugins already point at hosted MCP servers through the proxy. Bridging them is plumbing, not new tools. Inside a workspace the agent reaches the same servers through superset mcp call-tool.
  • Org-level integration_connections are inbound webhooks for triggers. They stay that way.
  • Notion and Sentry become plugins with an mcp block. Google has no hosted server. Decision 6.

05Tool policy

06Memory

  • Scope is the channel. Public-channel memory is readable org-wide; private channels keep their own store; DMs keep per-person notes.
  • Written three ways: "@Superset remember for this channel: …", the agent's own curation turn after a session, and past thread transcripts on request.
  • Steers participation: "answer deploy questions without being tagged" and "only respond when mentioned" are both memory entries.
  • Editable by anyone in the channel. "@Superset what do you remember about this channel?" lists it.
  • Store notes and ids, not Slack content. Pull messages live when needed.

07Mechanics

  • Dedup: ack retries by header, QStash deduplicationId: event_id, dedupe mention plus message on channel and ts.
  • Outbox: every reply recorded with an idempotency key before sending. No double posts, no lost replies.
  • Output: markdown block, streaming, feedback buttons.
  • Models: channel session on Haiku 4.5, low effort, no tools. Working session on Sonnet 5, Opus 5 in the picker, adaptive thinking, prompt caching.
  • Loop breakers: per channel-and-bot rate limit; never reply to a bot without a person in the loop.
  • Assistant pane: handle assistant_thread_started and context_changed.

09Decisions needed

  1. Where working sessions run. Recommended: cloud sandbox for channel threads, author's host for DMs, optional pinned runner host per channel. Alternatives: host-first with cloud fallback, or cloud-only. Section 03 has the comparison.
  2. Respond-automatically default. On like Claude Tag, or off until a channel opts in?
  3. Identity in channels. Per-user as proposed, or add channel service connections later?
  4. Approval quorum. Any linked member, or only the author?
  5. Gating. All Pro, or presence free and working sessions plus plugin tools paid?
  6. Google. Skip, or fund a bundled MCP server?
