# Replace `.superset/config.json` with `.superset/config.toml`

This ExecPlan is a living document. The sections `Progress`, `Surprises & Discoveries`, `Decision Log`, and `Outcomes & Retrospective` must be kept up to date as work proceeds.

Reference: This plan follows conventions from `AGENTS.md` (root), `apps/desktop/AGENTS.md`, `packages/trpc/AGENTS.md`, `packages/host-service/AGENTS.md`, and the ExecPlan template. The format itself was designed in `plans/20261003-superset-config-v2-format.md`; this plan implements it and repeats everything needed from it.


## Purpose / Big Picture

A repository tells Superset how to prepare and clean up a workspace through a file in the repository, `.superset/config.json`. Today its keys mean different things on a person's machine and in a cloud sandbox, cloud workspaces never run cleanup (every archived cloud workspace of this repository left a Neon database branch behind; 383 were deleted by hand on 2026-10-20), and the only way to edit it in the app is a three-tab editor that can only see three keys.

After this change a repository can write `.superset/config.toml` with four sections whose meaning is the same everywhere: `[install]` (optional preparation that does not depend on a workspace), `[setup]` (get this workspace ready), `[archive]` (release what `setup` created outside the workspace), and `[terminals.<name>]` (long-running commands such as a dev server). Any section can have a `[<section>.cloud]` or `[<section>.local]` table that changes it in one environment. A person can keep personal tweaks in a gitignored `.superset/config.local.toml`. Archiving a cloud workspace runs its `[archive]` commands, so a repository can delete what it created. Settings → project → **Workspace config** edits the whole file as text, with comments kept and errors shown as you type. Repositories that still have `config.json` keep working exactly as before, and Superset reports which old features are still used so they can be removed later.

To see it working: create `.superset/config.toml` in a project, create a workspace and watch the "Workspace Setup" terminal run the `[setup]` commands; press Run and see the default terminal's command; archive the workspace and see the `[archive]` output in the host-service log; open Settings → project and edit the file.


## Assumptions

The desktop app's older "v1" screens (the Electron-only workspace views under `apps/desktop/src/lib/trpc/routers/` and `apps/desktop/src/renderer/screens/main/`) are out of scope. They have their own JSON loader and keep reading `config.json`; see Open Questions Q1.

Cloud `[install]` has nothing to run it in this PR. Today the platform never runs the cloud meaning of `setup` either: an environment's saved image is prepared by an onboarding agent or by `packages/sandbox/src/environments/release.ts`. A separate daily-rebuild project (decision 12 in the format doc) will run `[install]` in the cloud. Until then `[install]` runs locally, before `[setup]`, and is documented as "cloud: used by environment rebuilds".

Only the first `default = true` terminal, in file order, drives the Run button in this PR. Several terminals, tracking them, and stopping them on archive come in a later PR together with port allocation and forwarding.

## Context and Orientation

Terms used in this plan:

A **workspace** is an isolated checkout of a repository where a person or agent works. Locally it is a git **worktree**: a second working folder of the same repository, created with `git worktree add`, which contains only files tracked by git (never gitignored files). The repository's first folder is the **main checkout**; its path is available to scripts as `SUPERSET_ROOT_PATH`. A **cloud workspace** is a workspace inside a remote Linux machine ("sandbox") hosted by Vercel; its files live under `/workspace`.

**host-service** (`packages/host-service`) is the background process that owns workspaces on a machine. The desktop app starts one locally; each cloud sandbox runs its own. It exposes **tRPC procedures**: typed remote functions, grouped into routers under `packages/host-service/src/trpc/router/`, called by the desktop app and by the API. The **API** is the hosted server; its procedures live in `packages/trpc/src/router/`. Released desktop and CLI builds keep calling old procedures, so `packages/trpc/AGENTS.md` requires changes to be additive: add new procedures or optional fields, never change what an existing one accepts, returns, or does. The host may be older than the client down to `MIN_HOST_SERVICE_VERSION` (`packages/shared/src/host-version.ts:32`), so a client calling a new procedure needs a fallback; `isMissingProcedure` in `packages/trpc/src/router/automation/relay-client.ts:123` detects an older host.

Today's config loader is `packages/host-service/src/runtime/setup/config.ts`. `loadSetupConfig({ repoPath, projectId, worktreePath?, homeDir? })` merges, per key, `<repo>/.superset/config.json`, then `<worktree>/.superset/config.json`, then `~/.superset/projects/<repoPath>/config.json` (falling back to `~/.superset/projects/<projectId>/config.json`), then overlays `config.local.json` from the worktree or else the main checkout, where each key may be an array (replace) or `{ before, after }`. `resolveScript(key, args)` returns `{ kind: "commands", commands, cwd? }` or, when a key has no commands, `{ kind: "script", scriptPath, cwd? }` for `.superset/<key>.sh`. Keys are `setup`, `teardown`, `run`, `start`, plus `cwd`.

Its callers are:
- `packages/host-service/src/trpc/router/workspace-creation/shared/setup-terminal.ts`: `startSetupTerminalIfPresent` opens a visible terminal labelled "Workspace Setup" with the setup commands joined by ` && ` (called from `trpc/router/workspaces/workspaces.ts:1354` on create and L557 on restore).
- `packages/host-service/src/runtime/teardown/teardown.ts`: `runTeardown` runs teardown in a hidden terminal with a timeout and returns `ok`, `skipped` or `failed`. It is used by the destroy pipeline (`trpc/router/workspace-cleanup/workspace-cleanup.ts`, `runDestroy`, step 2, blocking or best-effort, skipped when the workspace shares the main checkout), by `workspace.delete`, by `runtime/archived-workspace-reconcile.ts`, and by `projects/project-deletion.ts`.
- `packages/host-service/src/trpc/router/config/config.ts`: `getWorkspaceRunDefinition` resolves `run` from the main checkout for the Run button. The desktop picks between it and terminal presets in `apps/desktop/src/shared/workspace-run-definition.ts` (`selectWorkspaceRunDefinition`).
- `packages/host-service/src/runtime/sandbox-self-seed/sandbox-self-seed.ts`: `runSandboxStartHook` runs `start` on every cloud boot, each command as its own `{ cmd; }` line in `bash -lc`, detached, once per boot. The sandbox's boot script calls it through the host-service procedure `sandbox.runStartHook` (`trpc/router/sandbox/sandbox.ts:88`).

In the cloud, the API reads the committed file from GitHub in `packages/trpc/src/lib/sandbox/repo-hooks.ts` (`readRepoHooks`, schema `repositoryHooksSchema`: `setup`, `start`, `ports`), called only from `claim.ts:108` when a workspace is provisioned; only `ports` is used, to publish ports. Archive is `cloudWorkspace.delete` (`packages/trpc/src/router/cloud-workspace/cloud-workspace.ts:675`), which queues the reap jobs in `reap.ts`. The API reaches a sandbox's host-service with `addressSandbox(row, "address" | "wake" | "restart")` (`cloud-workspace.ts:109`), `mintSandboxGateAccess` (`packages/trpc/src/lib/sandbox/access.ts:20`) and `hostServiceMutation` (`relay-client.ts:92`, default timeout 25 seconds), as `generateDescription` does at `cloud-workspace.ts:613`.

The Settings editor is `apps/desktop/src/renderer/routes/_authenticated/settings/v2-project/$projectId/components/V2ProjectSettings/components/V2ScriptsEditor/V2ScriptsEditor.tsx` (three autosaving tabs, through host-service `config.getConfigContent` and `config.updateConfig`), passed as `scriptsEditor` into `V2ProjectSettingsBody.tsx`, under the section "Project lifecycle scripts". The code editor is `apps/desktop/src/renderer/routes/_authenticated/_dashboard/v2-workspace/$workspaceId/hooks/usePaneRegistry/components/FilePane/registry/views/CodeView/components/CodeEditor/CodeEditor.tsx` (CodeMirror; props `value`, `language`, `readOnly?`, `onChange?`, `onSave?`, and others).

Usage events go through `ctx.api.analytics.captureEvent.mutate({ source: "host_service", event, properties })`, as `trackWorkspaceEvent` does in `packages/host-service/src/workspaces/local-workspace-store.ts:62`. `HostServiceContext.api` is available in the setup terminal path and the destroy pipeline.

Affected: desktop app (renderer settings, shared run selection), host-service, API (`packages/trpc`), `packages/shared`, docs (`apps/docs`), prompts in `packages/shared/src/cloud-agent-launch.ts`, the desktop sidebar setup card, and `plugins/superset/skills/setup`. No database migration. No Electron IPC channel (all calls are host-service tRPC).


## Plan of Work

### Milestone 1: shared config package

Create `packages/shared/src/project-config/` and export it as the subpath `@superset/shared/project-config` in `packages/shared/package.json` (`exports`), pointing at `index.ts` like the other subpaths. Add `smol-toml` to `packages/shared/package.json` dependencies. The module must not import `node:` modules, so the renderer can use it. Files, one concern each, with co-located tests:

`schema.ts`: zod schemas, strict (unknown keys rejected), for the v2 file. A phase table (`install`, `setup`, `archive`) has `run` (string or string array), `cwd` (string), and optional `cloud` and `local` tables of the same shape without nesting. A terminal (`terminals.<name>`) has `run`, `default` (boolean), `cwd`, `cloud`, `local`. A port (`ports.<name>`) has `default` (integer 1–65535, required), `label`, `preview` (boolean). Names of terminals and ports match `^[a-z][a-z0-9_]*$`. At most 13 ports may have `preview = true`.

`parse.ts`: `parseProjectConfig(text: string): { ok: true; config } | { ok: false; errors: ConfigError[] }`, where `ConfigError` has `message` and, when known, `line` and `column` (from `smol-toml`'s `TomlError`, and from the zod issue path mapped to the first line that declares that table). This is what both the loader and the Settings screen use.

`resolve.ts`: `resolveProjectConfig({ base, local, environment }: { base: ProjectConfig; local: ProjectConfig | null; environment: "local" | "cloud" })`. It applies, in order, the base file, its `.cloud` or `.local` tables for `environment`, then `local` when `environment === "local"`. Merging is key by key: a value set by a later layer replaces the earlier one, arrays included; a table or terminal added by a later layer is added. It returns plain resolved phases (`commands: string[]`, `cwd?`) for `install`, `setup`, `archive`, the resolved terminals in file order, and the ports.

`v1.ts`: `fromV1Json(json: unknown)` converts a v1 object to the v2 shape (`setup` → `setup`, `teardown` → `archive`, `run` → `terminals.dev` with `default = true`, top-level `cwd` copied into each table; `start` → `setup.cloud`; `ports` → `ports.p<number>` with `preview = true`), and `toTomlText(config)` writes it with `smol-toml`'s `stringify`. Used by the Convert button and the legacy path.

Tests in `packages/shared/src/project-config/*.test.ts` cover: the reference file from the format doc parses; `web-ui` as a name fails with a clear message; an unknown key like `defualt` fails with its line; `.cloud` merge keeps a shared `cwd`; `run = []` disables; local file replaces arrays; v1 translation of this repository's current `.superset/config.json`.

Acceptance: `cd packages/shared && bun test src/project-config` passes, and `bun run typecheck` at the root has no errors.

### Milestone 3: cloud

Archive: add a host-service procedure `sandbox.runArchiveHook` (mutation, input `{}`, output `{ status: "ok" | "skipped" | "failed", outputTail?: string }`) in `trpc/router/sandbox/sandbox.ts`, using the same runner as `runTeardown` with the resolved cloud `archive` phase and the same 60-second limit as a local archive (`TEARDOWN_TIMEOUT_MS`). ### Milestone 4: Settings → Workspace config

Host-service, in `trpc/router/config/config.ts`, add two procedures, leaving the existing four unchanged:
- `getConfigFiles` (query, `{ projectId }`) returns `{ shared: { fileName: "config.toml" | "config.json", path, content } | null, local: { path, content } | null }`, reading from the main checkout.
- `writeConfigFile` (mutation, `{ projectId, file: "shared" | "local", fileName: "config.toml" | "config.json", content }`) validates with the shared parser (TOML) or `JSON.parse` plus v1 checks (JSON), refuses invalid content with `BAD_REQUEST` carrying the errors, and writes the exact text. Writing `config.toml` when `config.json` exists is allowed (Convert); the JSON file is left for the person to delete.

Replace `V2ScriptsEditor` with a new `WorkspaceConfigEditor` component at `.../V2ProjectSettings/components/WorkspaceConfigEditor/` (one component per folder, `index.ts` barrel). Section title "Workspace config", description "The commands Superset runs to set up, run and archive this project's workspaces. Saved to .superset/config.toml in the repository." Behaviour:
- Tabs: "Shared" (the file's path shown) and "Personal (config.local.toml)", with a note that the personal file is gitignored and applies to every worktree.
- The editor is a monospace `Textarea` from `@superset/ui`. Errors from `parseProjectConfig` appear under it with line numbers as you type.
- **Save** is explicit, disabled while invalid or unchanged; Mod-S also saves. No autosave.
- When the project has only `config.json`, a **Convert to config.toml** button fills the editor with `toTomlText(fromV1Json(...))` for review; saving writes `config.toml`.

## Validation and Acceptance

In the desktop dev app (`bun dev`), with a project whose repository has `.superset/config.toml`:

1. Create a workspace. The "Workspace Setup" terminal runs the `[install]` then `[setup]` commands.
2. Press Run. It runs the first `default = true` terminal's command.
3. Archive the workspace. The host-service log shows the `[archive]` commands' output, and the worktree is removed.
4. Put `[setup] run = ["echo personal"]` in the main checkout's `.superset/config.local.toml`, create another workspace, and see "personal" in its setup terminal.
5. Settings → project → Workspace config: type `defualt = true` under a terminal; an error with its line appears and Save is disabled. Fix it and save; comments in the file are still there.
6. In a project with only `config.json`: everything behaves as before, and Convert to config.toml produces the translated file.

In a cloud workspace whose repository has `[archive.cloud] run = ["echo archived > /tmp/archive-proof"]` style commands that call out (for this repository, deleting the Neon branch): archive it, wait about a minute, and confirm the branch is gone (`neonctl branches list`). Unarchive within 7 days and confirm `setup` re-creates it.


## Idempotence and Recovery

All steps are code edits and can be repeated. No database migration. Converting a repository writes `config.toml` next to `config.json`; deleting `config.toml` returns the repository to v1 behaviour. If the cloud archive hook misbehaves, the stop job logs and continues, so archiving still works; the hook can be disabled per repository with `[archive.cloud] run = []`.
